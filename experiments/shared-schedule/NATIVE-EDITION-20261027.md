## 为什么用 Taro 原生页面

该目录基于旧 R10 迁移实验更新，直接从当前 Stats 源码生成公开 JSX/CSS，数据计算引用同仓库的原始模型。转换生成物不手工修补。原生组件、路由、选择器、弹窗、分享、存储和联网放在平台边界。它不是网页嵌入，也不是另行手写一套赛事计算。

## 运行

保留本目录位于完整 Stats 仓库的 `experiments/shared-schedule` 下。在仓库根目录安装锁定依赖，再在本目录安装锁定依赖。执行 `npm test` 和 `npm run build:weapp`。官方微信开发者工具打开本目录，AppID 为现有“薯条杯赛事助手”；不使用测试号替代。

`prepare:design` 会审计所有注册页面的静态导入闭包。网页账号、大厅、反馈写入、Web 路由和 React DOM 控制器进入原生闭包时应失败。`build:weapp` 检查每包不超过 2 MiB、总包不超过本项目 20 MiB 预算。`project.config.json` 保持 `urlCheck: true`，不以关闭域名校验作为真机通过条件。

本机暂复用了现有依赖目录的 junction，未修改其内容。跨电脑复现仍需按锁文件独立安装，不能依赖 Z 盘的 junction。

## 对设计审阅文档的判断

页面归属、返回路径、移动首屏、触控尺寸和辅助字可读性的检查方向成立。但以下项目要区分：

1. 未登录的公开关注必须保留，不能因为统一“我的空间”而引入登录门槛。
2. 栏目名称和具体页面标题可以有层级差异，例如“数据排行”下的“选手排行”；不同用途的选中状态也不必强行同形。
3. 登录弹窗和直达的重置密码、邀请、验证链接需要共用组件和状态规则，不能简单删除独立流程页。
4. “我的比赛、待办、比赛提醒”涉及账号与权限，不能作为只读 MVP 的现成功能。微信身份接入必须由后端证明绑定关系，不能按邮箱字符串或公开选手名字自动合并账号。
5. 文档的主体类目、备案、后台运行和订阅消息结论部分来自较旧的二手资料，不能据此宣称可提审。提交前需在当前小程序后台及微信官方材料逐项确认，尤其是已选服务类目、服务器域名、隐私说明与功能范围。
