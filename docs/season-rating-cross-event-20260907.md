# 全高杯与学院赛评分检查 · 2026-09-07

这轮最重要的发现是学院赛公开快照存在重复统计，当前本地评分去重也未拦住。应先解决这个确定的数据问题。模型方面，全高杯与学院赛的追加回放没有支持立即替换 v1.4 公式；学院赛去重后的同队比较提供了一定统计表现信号，全高杯的验证样本较少。

本轮使用正式公开数据和当前本地评分代码，未修改应用代码、网页正式数据或发布版本。下面的评分变化是本地重算结果，不代表已核实线上前端正在运行同一版本。

## 数据来源与固定方法

检查时公开接口返回全高杯 V30、学院赛 V5，随后读取固定版本，避免分析过程中数据变动：

- [全高杯 S4 V30 正式快照](https://admin.fries-cup.com/api/public/seasons/QGCS4/publish/30/data)：19 支队伍、116 位注册选手、44 场比赛；其中 36 场正常赛果比赛进入时间回放。
- [学院赛 V5 正式快照](https://admin.fries-cup.com/api/public/seasons/FCA26/publish/5/data)：30 支队伍、191 位注册选手、127 场比赛；其中 117 场正常赛果比赛进入时间回放。

本地 `qgcs4_preseason_public.json` 是无比赛统计的赛前占位文件，本轮没有将它当成全高杯实际数据。

沿用上一轮的方法：比赛日之前重建英雄基线、个人历史与队伍 Elo，同一天先全部预测再加入当天结果，关闭冻结基线。个人预测检验仍要求赛前本职责至少 6 图、60 分钟、3 场，当场统计至少 10 分钟。没有因全高杯较短而放宽门槛。

各赛事使用自己的历史拟合参数，沿用固定公式和门槛，没有搜索更有利的参数。这是追加赛事的回溯检查，不是从未接触过数据的外部盲测；仓库已有学院赛评分回放工具。目标仍是现有统计分定义下的后续表现，没有独立的瞄准、站位或决策技术标签。

## 学院赛：先处理重复日志

学院赛 `match_logs` 同时包含导入历史与正式比赛日志。同一选手、同一正式比赛、同一地图的英雄、职责、时长及六项统计完全一致，但 `rawMatchId` 不同。当前 `src/lib/ratingBaselines.js` 第 103–113 行将正式 ID 和原始 ID 一起放入去重键，所以两份都会进入评分。

逐条与比赛详情的地图统计核对后，确认：

| 核对项 | 结果 |
| --- | ---: |
| 正式地图统计行 | 3,010 |
| 当前评分收集到的有效日志 | 5,480 |
| 多算的有效日志 | **2,470** |
| 涉及选手 / 比赛 | 181 人 / 96 场 |
| 英雄、职责、队伍 ID、时长、六项统计冲突 | 0 |
| 正常比赛日志：原始 → 每条计一次 | 5,400 → 2,960 |
| 正常比赛累计选手分钟：原始 → 每条计一次 | 58,677.67 → 32,338.50 |

正常比赛的累计选手分钟多计约 **81.4%**。这不是比赛实际持续时间，而是所有选手出场分钟之和。

分析副本使用已与正式地图统计逐条吻合的 `live_match_logs` 作为唯一 `match_logs`。要求两边覆盖完全一致，每个选手地图只出现一次；存在统计冲突、缺少记录或不明地图即停止处理。球队名称文字差异不当作新统计，身份按正式队伍 ID 核对。其余集合、统计总表、比赛结果和名单保持原样。

用真实的 `getLeaderboardEntries` 入口重算整个赛季，结果如下：

- **99 个选手职责条目的可显示 OVR 发生变化，涉及 98 位选手，最大相差 5 分。**
- 例如 `FCA26-P0014:DPS` 从 85 变为 80；其评分日志来源分钟从 383.383 变为 220.533。这里只报告确定的输入变化，不据此评价该选手技术。
- 完整赛季的正式 / 暂定 / 未评级数量未变，仍为 169 / 20 / 5 个职责条目。
- 历史回放的可检验观测从 661 条变为 642 条；原始输入额外纳入了 19 条。能够组成赛前队伍阵容的胜负预测从 98 场变为 81 场。重复时长会改变历史样本资格，不能只看最终正式人数。

去重前后还会改变历史基线及统计目标，不能把两次回放 MAE 的差值直接解释成模型性能提升。学院赛以下分析均使用地图核对副本；原始快照结果单独保留在 `fca26-export/validation`。

全高杯的 1,240 条评分日志与 1,240 条正式地图统计完整吻合，没有同类重复；核对副本与原始数据的评分结果一致。

## 当前 OVR 有多少参考价值

只比较同队、同职责、共同完整出场地图上的下一场统计表现；双方赛前均已正式合资格，共同时间至少 10 分钟。预测同分计半分，真实目标同分排除并计数。配对场次有重复队友，不能当成彼此独立的选手样本。

| 赛事 | 个人预测观测 / 比赛 / 日期 | 同队配对场次 / 不同配对 | OVR 配对匹配率 |
| --- | ---: | ---: | ---: |
| 全高杯 S4 | 88 / 11 / 5 | 35 / 22 | **62.9%** |
| 学院赛，地图核对后 | 642 / 73 / 18 | 241 / 57 | **69.7%** |
| 常规赛，前轮参照 | 474 / 60 / 18 | 169 / 57 | 62.7% |

全高杯 35 个配对中，19 次方向正确、6 次预测同分，得到 22 个加权正确计数；不是 22 次完全正确。学院赛 241 个配对中，165 次方向正确、6 次预测同分。

全高杯 OVR 匹配率的探索区间，按比赛日聚类约为 51.1%–76.1%，按队伍聚类约为 45.0%–79.2%。只有 5 个检验日期，且后期留存队伍占比较高，不能据点估计宣称稳定识别技术强弱。

学院赛的两个探索区间分别约为 62.8%–76.7%、63.0%–75.2%；按不同队友配对等权后仍为 69.4%。这支持“同队同职责下有一定统计表现参考价值”，不能转译成“技术评分准确率 69.7%”。输出为 66.9%（121 个配对），支援为 72.5%（120 个配对）；没有同队同职责的重装配对，不能外推。

跨队选手在同日同职责中的 OVR 成对匹配率为全高杯 70.5%、学院赛 58.4%。它们与上表是不同队列、不同加权，不能相减当作同队控制的因果收益，也不能凭赛事间的百分比高低判断哪项赛事评分更准确。

## 上一轮候选能否在另外两个赛事起作用

下表是未来原始表现分的平均绝对误差，每场先平均选手误差，再对各场等权；越低越好。只在同一赛事同一列比较，不能把不同赛事的误差大小直接当作模型优劣。

| 方法 | 全高杯 S4 | 学院赛，地图核对后 | 常规赛参照 |
| --- | ---: | ---: | ---: |
| 当前样本收敛分 | 10.427 | 12.446 | 11.831 |
| 同职责历史均值 | 9.342 | 12.347 | 11.268 |
| 之前固定的职责收敛候选 | 9.757 | 12.286 | 11.340 |
| 之前固定的团队项 K=4 | 10.563 | 12.913 | 12.088 |

职责收敛候选在全高杯仍未优于简单的职责均值；学院赛只比职责均值低 0.061 分，差值探索区间约为 -0.359 到 +0.271，尚不能证明稳定收益。学院赛排序匹配率相对当前原始分提高约 0.25 个百分点，幅度很小，且其他赛事没有一致的排序收益。

团队项在三个赛事的点估计均使误差增大。学院赛 K=4 的误差增加 0.467 分，探索区间约为 +0.213 到 +0.814；预先固定的 K=1、K=8 敏感性检查也均增大误差。这进一步削弱了立即接入这类历史团队补偿的理由。

历史同队分差方法在全高杯从当前原始分差的 19 次正确变为 20 次，在学院赛则从 167 次降到 162 次，没有一致的方向判断收益。共享加法团队项在同队两人相减时抵消，两个赛事均未改变任何同队原始分差。

胜负预测方面，按历史出场组成赛前阵容后，v1.3 与 v1.4 在全高杯均为 5/10，学院赛均为 48 次正确、1 次同分，共 81 场（59.9%）。这项团队结果检验也没有观察到对手校正带来的准确率提升，但不代表对手强度完全没有作用。

## 建议与验证记录

下一步优先修复学院赛日志去重：核对发布端历史与正式日志的合并方式，并在评分收集端防止同一正式统计因原始 ID 不同而重复计入。以正式比赛、地图、选手及统计内容确认身份，原始导入 ID 保留作溯源；不能一律丢掉历史日志或忽略有冲突的记录。修复后重算基线、OVR 和相关数据展示。

全高杯可暂时维持现有公式。模型升级继续使用这套固定检验方法，优先加入新比赛验证，不根据本轮结果继续选择参数。

本轮 43 项已有分析回归测试全部通过。新增核对脚本验证了统计冲突、缺少正式日志、不明地图、英雄不一致四类输入会被拒绝。两个赛事的团队及收敛报告独立重算一致，拟合日期全部早于预测日期，应用评分代码、正式本地数据及前轮报告哈希未变。

完整证据位于 `artifacts/season-rating-cross-event-20260907/`：

- `sources.json` 与 `inputs/`：固定版本地址、抓取时间、文件 SHA-256、原始快照及学院赛分析副本。
- `data-audit.json`：2,470 个重复身份、逐项 OVR 变化和来源分钟。
- `report.json`：跨赛事汇总；各赛事子目录保存逐日预测、参数、原始检验及候选报告。
- `verification.json` 与 `regression-tests.log`：验证记录。

可从仓库根目录运行以下命令重新核对已保存数据与报告，不会写入应用代码或正式数据：

```powershell
node artifacts/season-rating-cross-event-20260907/audit-snapshots.mjs
node artifacts/season-rating-cross-event-20260907/build-summary.mjs
node --test scripts/assertSeasonRatingValidation.mjs scripts/assertSeasonRatingCalibration.mjs scripts/assertSeasonRatingDiagnostics.mjs scripts/assertSeasonTeamModelAnalysis.mjs
node artifacts/season-rating-cross-event-20260907/verify.mjs
```

原始时间回放使用现有 `scripts/validateSeasonRatings.mjs --season <赛事 ID> --input <快照> --output <独立目录>`，再依次调用同目录已有的诊断、团队和收敛脚本，全部显式指定该赛事输入与基础验证报告。没有改写任何一轮原有报告。
